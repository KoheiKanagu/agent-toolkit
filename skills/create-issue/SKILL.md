# issue 作成

## 出力の契約

- 成果物は GitHub issue（URL）。受け入れ条件に「〜すること」と「〜しないこと」が両方含まれる。
- 報告で URL と受け入れ条件を出す。実装には入らない。
- 「文面だけ」「投稿しないで」と明示されたときだけ、会話に本文を出して完了とする。

受け入れ条件は要件の文。種類ラベル（完了 / NG / 壊さない など）は付けない。

## 手順

1. **対象リポジトリを決める**: ユーザーが名指しした GitHub リポジトリ。無ければ作業ディレクトリの GitHub remote が1つならそれ。複数・不明・迷うなら対象なし。
2. **投稿するかを決める**: 対象リポジトリが決まり、受け入れ条件が書けるなら投稿する。「文面だけ」「投稿しないで」なら投稿しない。対象なし、または受け入れ条件が書けないなら投稿せず `AGENTS.md` の外部書き出しに従う。
3. **書式を決める**: 対象リポジトリがあるとき、次をこの順に探し、最初に見つかった書式に従う。対象なしなら最小構成。
   1. `.github/ISSUE_TEMPLATE/` の該当テンプレ（種類が会話から一意。複数あり選べなければユーザーに1問し、この返答では他を聞かない）
   2. `.github/ISSUE_TEMPLATE.md`
   3. プロジェクト `AGENTS.md` の issue 書式
   4. `CONTRIBUTING.md` の issue 書式
   5. どれも無ければ最小構成
4. **短い本文を書く**。
5. 投稿する場合は作成して URL を報告する。投稿文の `#` + 数字は `skills/git-workflow` に従う。
6. 報告で受け入れ条件を引用する。ユーザーが確認するまで実装しない。同じターンで実装しない。

## 最小構成（プロジェクト書式が無いとき）

```
## 現状

（数行。直し方は書かない）

## 受け入れ条件

- XXすること
- YYしないこと
```

## 判断基準

- **「issue を書いて」「作って」「立てて」「切って」のとき**: 投稿する。人間が後から直す。
  - ❌ 「issue を書いて」→ 会話に本文だけ返す
  - ✅ 「issue を書いて」→ GitHub に作成する。「文面だけ」なら会話に返す
- **本文の分量**: 現状と受け入れ条件で止める。パス一覧、スタック、検証コマンド、実装メモ、チェックリストは書かない。理由: 初稿は人間が確認／直す用で、実装手順ではない。
- **プロジェクトに issue テンプレがあるとき**: 必須欄と、受け入れ条件・AC・Acceptance Criteria・Done があればそこに「〜すること / 〜しないこと」を書く。任意欄は空のまま。欄が無ければ `## 受け入れ条件` を足す。
- **受け入れ条件を書くとき**: テストや画面で判定できる文にする。直し方は書かない。ラベルは付けない。「すること」を1つ以上、「しないこと」を1つ以上置く。既存を壊す余地があるなら「しないこと」に入れる。
  - ❌ 正しく動くこと
  - ❌ リトライを足す
  - ✅ 同じリクエストを2回送っても課金行は1行であること
  - ✅ 外部 API が 500 のとき内部が二重送信しないこと
- **受け入れ条件が書けないとき**: 投稿も本文も出さず、「直ったら何が起きていればよいか」を1問確認する。理由: 書けないのは仕様が無い。確認は1トピックに限る。
- **本文を出したあと**: ユーザーが受け入れ条件を確認するまで実装に入らない。
